Section 1

The Problem
Manual Test Case Writing

⏳

Slow & Repetitive

QA engineers spend significant time writing boilerplate test cases — especially for standard form fields (text inputs, amounts, buttons) that follow predictable patterns every time.

❌

Inconsistent Coverage

Different testers produce different quality test cases. Common checks like "required field validation" or "spelling/grammar" are sometimes missed entirely.

🔄

Context Switching

Analysing a requirement document, mapping it to form fields, and writing test cases in a spreadsheet requires constant context switching and is error-prone.

💰

Cost of Cloud AI

Existing AI-powered tools rely on cloud APIs (OpenAI, Gemini) which add ongoing per-token costs and raise data privacy concerns for enterprise requirements.

Section 2

Project Overview

A locally-hosted, free, privacy-preserving web tool that generates structured QA test cases in seconds.

🖥️

Local-First AI

Runs on Ollama with the Mistral model — entirely on your machine. Zero cloud API costs, zero data leaks.

📋

Structured Output

Generates test cases with TC ID + Scenario + Expected Result — exactly the columns your QA spreadsheet needs.

📷

Screenshot OCR

Upload a screenshot of any form. Tesseract reads the text, Mistral identifies fields — no manual typing required.

Core Goal: A QA engineer should be able to go from a form screenshot (or a list of field names) to a fully-formatted, downloadable Excel test case sheet in under 60 seconds.

Section 4

4-Step User Interface

1
Define Custom Fields / Buttons — Add fields with a type (Text / Amount / Button) and a name. Check "Data Field" for text fields that drive other field population.
2
Upload Screenshots (Optional) — Upload screenshots of any form. OCR extracts the text, Mistral identifies field labels and types, and auto-populates Step 1.
3
Enter Requirement Text (Optional) — Plain English description of the feature. If only this is provided, 8–10 coverage test cases are generated. Also supports document upload (UI placeholder).
4
Review & Download — Test cases display as cards showing TC ID, Scenario, and Expected Result. Click "Download as Excel" to get a formatted .xlsx instantly.
At minimum, you need either a field or a requirement — not both. The tool works with any combination.
Section 6

Field Types & Their Rules

📝

Text Field 1 TC

  • Standard text input, dropdown, date, code, or description field
  • Generates 1 test case: input limit + valid save check
  • Template: "Verify whether the [field] has an input limit and whether the entered amount can be successfully saved"
🔗

Data Field 3 TCs

  • A special text field whose value populates other fields below (e.g., Customer ID, Policy Number)
  • Enabled via "Data Field" checkbox
  • 3 test cases: valid entry → invalid entry → values load correctly in downstream fields
🔢

Amount Field 2 TCs

  • Numeric, monetary, or quantity fields
  • Generates 2 test cases: valid input acceptance + error on negative/zero values
  • Never gets a "loads values" test case (unlike Data Fields)
🔘

Button 1 TC

Buttons (Add, Delete, Submit, Search, Clear, etc.) each generate 1 test case verifying the button performs its intended action without errors. These are handled entirely client-side without LLM involvement.

Section 6

Anatomy of Every Generated Set

★

↓ LLM-generated TCs for each field (renumbered after grammar TC) ↓
B

S

TCn

TCn+1
Form highlights empty required fields when Save is pressed
TCn+2
Save works when every required field is complete
Section 5

Screenshot OCR Pipeline

1
Upload — User selects one or more screenshots via file input
2
Grayscale — Pillow converts each image to grayscale (img.convert('L')) for improved OCR accuracy
3
Tesseract OCR — pytesseract.image_to_string(img) extracts raw text from each image
4
Combine Text — OCR output from all images is joined into one block of text
5
Mistral analysis — Combined text is sent to the local LLM with a prompt to identify field labels and types
6
Parse & Deduplicate — Lines parsed (format: Label: type), duplicates removed, fields auto-added to Step 1

Mistral's Field-Type Rules

  • Keyword match: "button", "btn" → button
  • Keyword match: "amount", "number", "numeric", "currency", "quantity" → amount
  • Everything else → text

Constraints applied

  • Field names longer than 80 characters are discarded
  • Deduplication is case-insensitive
  • Low-temperature (0.3) for deterministic field detection
Requirement: Tesseract must be installed at C:\Program Files\Tesseract-OCR\tesseract.exe (Windows). The app checks and configures the path automatically at startup.
Section 7

AI Prompt Engineering

The prompt sent to Mistral is highly structured to force predictable, countable output:

Key Prompt Sections

  • Field Inventory — Explicit count of each field type, total TC count pre-calculated
  • Generation Rules — Per-type TC templates word-for-word
  • Output Format — Forces pure JSON, no markdown, no extra text
  • Verification Checklist — A ✓ checklist the model must pass before returning
  • Temperature 0.7 — Balanced between creativity and consistency
The prompt tells Mistral: "TOTAL EXPECTED TEST CASES: N (MUST be exactly this number)" — pre-computing the exact count prevents under/over-generation.
// Example prompt structure (simplified) "FIELD INVENTORY (COMPLETE LIST): - REGULAR TEXT FIELDS: 2 → 2 TCs - Customer Name - Address - DATA TEXT FIELDS: 1 → 3 TCs - Customer ID - AMOUNT FIELDS: 1 → 2 TCs - Loan Amount TOTAL EXPECTED: 7 (MUST be exactly 7) === GENERATION RULES === FOR EACH REGULAR TEXT FIELD: Generate EXACTLY 1 test case Template: Verify whether [field] has an input limit... OUTPUT FORMAT (CRITICAL): Return ONLY JSON - no markdown:" {"test_cases": [ {"id": "TC01", "scenario": "...", "expected_result": "..."} ]}
Section 8

Hallucination Prevention

LLMs sometimes invent fields that were never mentioned. The app has two layers of defence.

🚦

Layer 1 — Prompt Guardrails

The prompt includes a bold warning:

"*** CRITICAL: ONLY use the fields provided below. Do NOT make up, assume, or hallucinate any fields. ***"

Combined with explicit field inventory and exact expected count forces the model to stay within bounds.

🔎

Layer 2 — Post-Generation Filter

After the LLM responds, every test case is scanned:

for tc in test_cases: scenario = tc['scenario'].lower() valid = any( field in scenario for field in provided_fields ) if not valid: # discard — hallucinated field print("FILTERED OUT", tc)

Only test cases that reference an actual provided field name pass through.

This two-layer approach (prompt constraints + runtime filtering) prevents the LLM from writing test cases for fields the user never defined.
Section 7

Robust JSON Extraction

LLMs don't always return clean JSON — the backend handles messy responses gracefully.

1
If the response contains ```json ... ``` markdown fences, strip them
2
If it contains plain ``` ... ``` fences, strip those instead
3
Find the first { and last } — extract just that JSON object regardless of surrounding text
4
Parse with json.loads() and extract test_cases array
5
If parsing fails, log the full raw response and return [] — never crash the server
# Strip markdown fences if '```json' in text: text = text.split('```json')[1] .split('```')[0].strip() elif '```' in text: text = text.split('```')[1] .split('```')[0].strip() # Find JSON boundaries start = text.find('{') end = text.rfind('}') + 1 if start != -1 and end > start: text = text[start:end] # Safe parse try: data = json.loads(text) test_cases = data.get('test_cases', []) except json.JSONDecodeError as e: print(f"Parse failed: {e}") return []

Frontend Deep Dive

JavaScript Architecture

State Management (plain arrays)

customFields[] — in-memory array of field objects {id, type, name, is_data_field}

currentTestCases[] — stores the last API response for export

Field Rendering (DOM re-render)

Every change (add, type switch, name input, delete) triggers a full re-render of the field list via renderFields(). Clean and simple — no virtual DOM needed at this scale.

Type-Driven Checkbox Visibility

The "Data Field" checkbox only renders for fields with type="text". When switching to amount/button, the checkbox disappears and is_data_field flag is effectively ignored.

Key Event Handlers

  • addFieldBtn → addFieldEntry()
  • generateBtn → handleGenerate()
  • exportBtn → handleExport()
  • resetBtn → handleReset()
  • screenshotsInput.change → OCR fetch

Loading / Error States

  • .hidden CSS class toggled for spinner and error div
  • Button disabled during OCR to prevent double-submit
  • Errors shown inline — no modal/alert boxes

Excel Download (client-side)

Response is converted to Blob, turned into an object URL, and a hidden <a> tag is programmatically clicked — no page navigation needed.

Section 11

Current Limitations

�

Powerful Models Cannot Run on Company Laptops

Company-issued laptops lack the GPU memory and compute required to run large, capable language models locally. The tool is therefore limited to smaller models like Mistral 7B — which, while functional, produce noticeably weaker and less nuanced test cases compared to frontier models.

☁️

Cloud-Based AI Is Not Viable Due to Cost

Powerful cloud models such as GPT-4o or Claude 3.5 would significantly improve output quality, but their API costs are prohibitive for internal tooling at scale. Without a budget allocation or enterprise agreement, the project cannot leverage the AI models that would make it most effective.

🔍

OCR Quality is Unreliable

Tesseract uses only grayscale conversion before OCR — no binarisation, deskewing, or upscaling. Low-resolution screenshots, stylised fonts, dark backgrounds, or overlapping UI elements cause missed or garbled field labels, leading to incorrect test case generation.

⚠️

Manual Review Is Always Required

Because the tool is forced to use weak local models (hardware barrier), cannot access powerful cloud models (cost barrier), and relies on error-prone OCR for screenshot input, the accuracy of generated test cases cannot be guaranteed. Every output must be carefully reviewed and corrected by a QA engineer before use.

Core Constraint: The tool's effectiveness is directly bottlenecked by model quality. Until hardware or budget constraints are resolved, the AI will remain underpowered relative to the task — making human oversight non-negotiable.
Section 12

Future Work &
Improvements

☁️

Affordable Cloud API — Bypass Laptop Limits

Addresses: hardware constraint & cost barrier.
Integrate Groq API (free tier, extremely fast inference) or leverage an existing Azure OpenAI enterprise agreement the company may already hold. The AI runs on the provider's hardware — no GPU needed on any employee laptop — and individual test-case generations cost fractions of a cent, making it manageable even on a small internal budget.

👁️

Vision-Capable LLM (LLaVA)

Addresses: unreliable OCR.
Replace the Tesseract OCR → Mistral text pipeline with a single LLaVA multimodal model call that reads the screenshot directly. No preprocessing, no garbled text — the model sees the UI exactly as the QA engineer does. LLaVA 1.6 7B can run on the same shared server, keeping the solution fully internal if needed.

🖥️

Shared Internal Server Deployment

Addresses: hardware constraint on individual laptops.
Host Ollama and the LLM on a single shared team machine (even a mid-range workstation with an 8 GB GPU is sufficient for Mistral 7B). QA engineers access the tool via browser over the local network — no individual setup, no laptop GPU requirement, and the entire team shares one inference engine.

✏️

In-Browser Review & Edit Workflow

Addresses: mandatory manual review overhead.
Make generated test case cards directly editable in the browser — inline fields for scenario and expected result — so QA engineers can review and correct AI output in one structured step before downloading. Reduces the back-and-forth between the tool and Excel during the unavoidable review phase.

Section 12 — Continued

Further Enhancements

🧹

Smarter OCR Preprocessing (Short-Term Fix)

While transitioning to LLaVA, improve the existing Tesseract pipeline immediately by adding adaptive binarisation (Otsu's method), deskewing, and 2× upscaling via OpenCV. This is a low-effort, zero-cost change that can improve OCR accuracy by 20–40% on typical UI screenshots without any model changes.

🔁

Modification Excel Upload

Complete the already-present UI placeholder: accept an existing test case Excel file, detect which fields have been added, removed, or renamed since the last run, and regenerate only the affected test cases — enabling incremental updates without regenerating everything from scratch each sprint.

🏷️

Priority & Severity Tagging

Automatically assign P1/P2/P3 priority and High/Medium/Low severity labels to each generated test case. This helps QA teams instantly identify which test cases to execute first during regression cycles, reducing the triage effort that is currently done manually in Excel.

📄

Document Parsing (PDF / DOCX)

Integrate PyMuPDF or python-docx to parse uploaded requirement documents and auto-populate the requirement text box. This eliminates the manual copy-paste step from spec sheets and is a straightforward backend addition using libraries already compatible with the existing Flask setup.

Deployment Path: Containerise with Docker and serve via Gunicorn + Nginx on the shared internal server — making the tool a stable, always-on resource for the whole QA team, not a per-laptop install.
